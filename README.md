# Pelican Test

A small [codex-proxy-rs (CPR)](https://github.com/zyycn/codex-proxy-rs) plugin for manual and scheduled SVG pelican animation tests. Each test sends one Responses request and records the result, timing, token counts, Client Key and routed account.

Starting with `0.5.0`, the plugin runs only its management page and background test scheduler. It no longer registers global HTTP middleware or supplies the `/v1/codex/responses` alias. CPR's native `/v1/responses` endpoint remains available.

## Pelican animation page

Open **鹈鹕** from the installed plugin's management pages. Select an enabled Client Key, a model visible to that Key, and a reasoning effort (default `low`), then click **开始测试**. One click sends one Responses request; account selection, access rules, quota and accounting remain with CPR. Loading the page reads available Key/model metadata and saved records without generating an animation.

The prompt is fixed, including the original spelling:

```text
用svg绘制一个2D鹈鹏骑自行车的动画的html，不要用skill，不用测试
```

The page consumes native Responses SSE or JSON. Each finished attempt appears under **生成记录**, newest first, with its manual/scheduled source, model, effort, Client Key, upstream account, outcome, timings and token counts. Click its thumbnail for a larger animation, or **源码** to see the original output. The dialog includes time to first content and options to copy the HTML or download it in standalone mode. Viewing a record never sends a generation request. Missing usage stays unknown. A response must complete and contain an SVG before the page marks it generated. Incomplete, failed and stopped attempts keep any available source and have their own status. **停止生成** cancels the current manual request.

History displays 20 records per page. Every new run is saved separately, and both modes still read records saved by older versions. The hosted archive shows the most recently saved runs first and retrieves the full source on demand for larger outputs. Opening a result does not use the model.

Standalone history uses the current browser and origin's storage quota. CPR stores history per plugin instance in PostgreSQL: the new run archive has 16 MiB and 10,000 storage items, with a separate index. A long result can use multiple items, so the number of saved runs depends on their sizes. One hosted record can be up to 900 KiB as JSON. If the archive is full or a result exceeds its size limit, the new result is reported as unsaved and all saved records remain available. A failed manual save can still be opened and copied while the page remains open. Scheduled save failures appear above the history table; they do not block the next scheduled run.

CPR records the non-secret Key ID/name and looks up the actual routed account by the gateway request ID, checking that the usage row belongs to that Key. Missing usage or account data stays unknown; the account ID can be shown when its display name is unavailable. Standalone records show a short Key fingerprint and cannot resolve the upstream account. Neither mode persists API Key secrets. Missing identity fields in older records are not backfilled.

### Schedule a test in CPR

Expand **定时测试**, choose a Client Key, a model and a reasoning effort, then enter a five-field Cron rule and an IANA time zone. For example, `0 9 * * 1-5` with `Asia/Shanghai` means 09:00 Monday through Friday in that zone. Select **启用计划** and **保存计划** to arm it. Each plugin instance has one plan; it is off until explicitly enabled. The panel shows the next eligible time. **暂停计划** stops future runs; any already claimed run can finish.

CPR runs the plan in its maintenance callback while the plugin and host are running, even with the browser closed. The plugin durably claims each eligible minute before issuing one Responses generation using the fixed prompt and the selected Key's normal routing and usage rules. CPR's callback interval means the request need not start at second zero. Missed minutes are skipped. A claimed minute is not retried across a restart, and an interrupted run is recorded when maintenance resumes and its claim expires. A model run has a 90-second ceiling, further bounded by the host's call budget. Results go into the same history table, which refreshes in a visible CPR page. Standalone mode only supports manual runs.

The pinned CPR management-page loader explicitly rejects nested iframe elements, injects `frame-src 'none'`, and uses `sandbox="allow-scripts"` without download permission. The hosted page therefore projects the generated SVG into an isolated image document, supporting SVG CSS/SMIL animation; it does not execute generated HTML scripts in the plugin page. Use **HTML 源码** and **复制 HTML** for the complete output. HTML/JavaScript-driven animations require the standalone mode described below. These boundaries follow the [pinned host page assembler](https://github.com/zyycn/codex-proxy-rs/blob/c622f085748f812936a7371fcc85d1621fa72ca8/frontend/src/views/plugins/management/frame.ts) and [iframe component](https://github.com/zyycn/codex-proxy-rs/blob/c622f085748f812936a7371fcc85d1621fa72ca8/frontend/src/views/plugins/components/PluginManagementFrame.vue).

### Standalone page

From the repository root, start the standalone page with Node.js 22 or newer:

```sh
node scripts/serve-pelican.mjs
```

Open `http://127.0.0.1:3217/` (or choose another port with `--port 3218`). No frontend build or dependency installation is needed. Choose **连接网关**, enter your gateway URL (with or without a final `/v1`) and **API 密钥（Client Key）**, and load its model list. This is the model API key, not an administrator key. When installed in CPR, the page hides this connection UI and uses the host bridge instead.

The local service listens only on `127.0.0.1` and exposes the page plus the two model API routes. It checks Host and Origin, forwards only the selected gateway's model-list and Responses requests, disables redirects, and does not store or log API keys. Browser requests go through this same-origin service, so the gateway does not need to permit cross-origin requests from a `file:` page. Stopping generation closes the upstream stream. Opening `web/pelican.html` directly remains available for layout preview, but direct gateway requests then require the gateway's CORS support. Connection failures are shown inside the open dialog with distinct network, timeout, HTTP 401, HTTP 403 and endpoint errors.

Standalone mode displays the generated HTML in a separate sandboxed iframe with inline scripts/styles permitted and external networking blocked, and offers HTML download. It uses the same fixed prompt and sends a single `POST /v1/responses` request. Opening the page or connecting only reads the model catalog; it never automatically generates an animation. Reconnect after reloading the page.

The plugin adds administrator-only `GET /bootstrap` and `POST /models` management routes to read non-secret Key summaries and the selected Key's model list. `GET /history` lists a page, `GET /history/record?id=…` opens a saved result, and `POST /history` appends a manual run. New runs use `pelican-archive` and `pelican-archive-index`; existing `pelican-history` data stays readable. `GET /schedule`, `POST /schedule` and `POST /schedule/pause` manage the plan in `pelican-schedule`. The plugin never reads account credentials. `web/pelican.html` is declared in both the author manifest and management registration; the existing packaging CLI collects it without an additional build step.

## Compatibility

- Source/package version: `0.6.0`.
- Requires CPR `>=3.44.0, <4.0.0` with manifest schema 2, RPC protocol 7, `management` 2, and `maintenance` 1. CPR checks the declared contract at install, version planning and startup.
- The official SDK and packaging CLI are pinned to CPR revision `c622f085748f812936a7371fcc85d1621fa72ca8` (`v3.44.0`). After a host upgrade within the range, check that the plugin still runs and the Pelican page opens.
- Stable plugin ID: `selfhosted.omp-native-bridge`. The legacy ID and state namespaces are retained so an existing instance can keep its saved runs and schedule.

The public release repository is [hl9565/codex-path-native-bridge](https://github.com/hl9565/codex-path-native-bridge). The Rust package/binary keeps its existing name, `cpr-omp-native-bridge`.

## Build and package

Requires Rust/Cargo `1.99.1` or newer, Git, Make and access to the pinned upstream source and Cargo dependencies. `Cargo.lock` is retained. Run from the repository root:

```sh
make test
make cli
make package
```

`make cli` installs the pinned official `cpr-plugin` packaging CLI into the repository's `.tools/`, not a global tool directory. `make package` builds the release binary and writes the installable archive to `dist/` using that CLI.

The default target is derived from `rustc --print host-tuple`. Build for the CPR host's operating system and architecture, not necessarily the development machine's. For example, on a matching Linux x86_64 host or with a configured cross-toolchain:

```sh
make package TARGET=x86_64-unknown-linux-gnu
```

An explicit target requires its Rust target components and a suitable linker/toolchain. A macOS package cannot be installed as a Linux plugin. Generated binaries, packages and local CLI tools are excluded from the source repository. Linux x86_64 packages and SHA-256 checksums are available in [GitHub Releases](https://github.com/hl9565/codex-path-native-bridge/releases); other targets can be built from source.

## Install in CPR

1. For a local build, choose **上传包** in CPR's **Plugin Management** and select the archive from `dist/`. To install a published version instead, choose **GitHub**, enter `hl9565/codex-path-native-bridge`, select a published tag and the Linux x86_64 archive, and leave download authentication set to none.
2. Review the version, target platform and SHA-256 before installing.
3. To keep your history and schedule, install the new artifact and switch the existing instance to it. If upgrading from `0.4.0`, CPR's version plan drops the old HTTP binding, and clients using its former alias need to use CPR's native `/v1/responses` endpoint.
4. Open **鹈鹕** from the enabled instance. Its management page uses existing CPR Client Keys and models; no plugin credentials are required.

### Trust and failure scope

CPR plugins run as trusted processes with the gateway's system identity. They can access its data, credentials, configuration and network; CPR does not provide a plugin security sandbox. Package/digest/compatibility checks do not prove code safety.

Since `0.5.0`, ordinary gateway traffic does not enter the plugin. Its calls on the CPR runtime panel are from plugin management and maintenance.

## Verification

Run `node --test tests/pelican-page.test.mjs tests/pelican-server.test.mjs` (or `make web-test`) to check the page and loopback service with mock responses and credentials. Run `cargo test --locked` to verify the plugin's management and maintenance registration, pagination, source preservation, quota handling, account lookup and schedule behavior.

The Linux x86_64 `0.6.0` package was tested on isolated CPR `3.44.0` using an in-place upgrade from `0.5.0`. The old result and schedule were retained. The test ran a manual and scheduled request against a loopback fixture, exercised concurrent saves and paging, reached the PostgreSQL archive quota, and restarted CPR. The archive still reported 48 saved runs after the rejected write and restart, and the test reopened the complete source of a split result.

The Linux x86_64 `0.5.0` package was verified on an isolated CPR `3.44.0` host by switching an existing `0.4.0` instance in place. CPR dropped the HTTP binding and retained the saved history and plan. A manual run and a scheduled run completed against a loopback fixture after the switch, and the scheduled plan was paused successfully.
